01 / Components

Components come from the design system

Ask AI to build something on a Miro board, and the design system MCP answers the first question: what is this actually supposed to look like?

The right sticky yellow, the right frame corners, the right connector, the right icon meaning the right thing. Made machine-readable, this is what lets a prompt produce a real, on-brand Miro object instead of a plausible-looking approximation—the same problem every design-system MCP solves, whether it’s Indeed’s buttons or New York State’s form fields.

That’s necessary. It’s not what this case study is about.

02 / Composition

Composition is the problem

Every other design-system MCP gets to treat composition as already solved, because its components live inside a screen.

A grid, a set of breakpoints, an edge—something underneath the component library decides where things go once the right component is picked. A button doesn’t need to know how far it sits from the next button; the layout system already handled that.

Miro’s canvas has no layout system underneath it. There’s no grid, no breakpoint, no edge. Handing AI the right components doesn’t tell it where they belong, how many of them should exist right now, or whether it’s allowed to place something on top of work a person already left there.

Composition—position, density, pacing, whitespace, sequence—isn’t inherited from anywhere on an infinite canvas. It has to be designed on purpose, as its own layer.

That gap is the actual subject of this case study.

03 / One example

One example, worked through in full

The clearest place to see the problem was a retrospective.

A retro is a container for honesty: people show up to say what went well, what didn’t, and what to change. The components were never the issue—the AI could already place a perfectly on-brand sticky note. The issue was composition: it would fill the container before anyone arrived, with plausible-sounding feedback no one on the team had actually said.

So the first composition rule was simple: leave the stickies empty. I wrote it three ways, each more specific than the last.

The rule, translated

One idea at three levels of specificity

Leave the stickies empty so teams can speak up

A retro is a container for honesty. Creating one means making it easy to show up, so the system should respect the room before placing anything.

Step 01

Principle

Clear enough for a team to agree on and use as a shared standard.

Intent
Generated boards should be usable immediately.

AI should
Create empty contribution areas for participatory work unless asked otherwise.

AI should not
Fill workshops with fake participant responses.

→
Step 02

Rule

Specific enough to check against a real board.

Interaction rule Do not invent session content
  • Leave participant contribution areas empty by default.
  • Only add sample content when the prompt asks for it.
  • Clearly label any sample as an example.
  • Never fabricate summaries, votes, or participant input.
→
Step 03

Spec

Specific enough for engineering to build.

# do_not_invent_session_content sticky_notes: default_content: empty sample_content: allowed: only_if_requested label: required participant_input: generate: false
The composition change

The components did not change. The composition did.

Before this rule, a generated retro could arrive already “finished”—three tidy columns of feedback nobody had said, built entirely out of correctly styled components. It looked like a retro. It wasn’t one.

After the rule, the same prompt produces a board with a clear entry, an empty middle where people add their own thinking, and an exit where the team votes and decides.

04 / From fix to system

Deciding it had to work everywhere, not just here

One good composition rule for one use case is a fix, not a system.

So I tested the same three-step translation—principle, rule, spec—against two more situations chosen on purpose: ideation workshops, which need room for wide-open thinking rather than just honesty, and project reviews, which need evidence and a decision rather than just contribution.

From one rule to a system

Four steps for turning composition judgment into shared infrastructure

Step 01

Define the principle.

Name the collaborative behavior the generated board needs to protect.

Step 02

Make it checkable.

Translate the principle into defaults, constraints, and exceptions.

Step 03

Test for transfer.

Run the same method across situations with different participation needs.

Step 04

Feed failures back.

Use weak outputs to revise the principles, rules, specs, and checks.

Three situations. Seven checks. One learning loop.

The scope was deliberately wide enough to test whether the method transferred, but narrow enough to inspect each failure.

Three starting contexts

Each situation needed a different kind of participation and a different kind of ending.

Composition beyond the retro

The failures were about arrangement, not identity

The method held up across all three situations, and it surfaced composition failures the first rule never touched—problems no component library could catch.

A board built entirely from correct components could still collide with existing sticky notes, crowd the canvas until nothing was left to focus on, contain a decorative timer instead of a working one, or end a workshop in an unstructured pile with no decision attached.

On an infinite canvas, position carries meaning. I defined a spatial grammar for hierarchy, direction, proximity, contextual anchors, tool placement, whitespace, and growth. New work should attach to meaningful context—not merely the nearest empty coordinates—and human-authored work should be preserved before AI-created material is reflowed.

05 / Evaluation

Seven checks, all about composition

Seven checks came out of the failures—every one of them a composition question, not a components question.

A perfectly on-brand sticky note can still fail all seven. When an output failed, I asked what it revealed about the system: an unclear principle, an over-broad rule, a conflict, or a missing exception.

06 / Outcome

Where it landed

What exists now

A way to test composition the same way the design system already tests components—not by taste, but against a specific, checkable rule. Components answer whether an object is recognizably Miro. Composition answers whether the board is recognizably good: usable immediately, honest about what people actually said, and respectful of what was already there.

What’s still open

How much this changed the real failure rate of generated boards in production, and whether the same three-step method holds as new use cases get added. That’s the next thing to measure, not a claim being made yet.
